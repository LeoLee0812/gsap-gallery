transform vs 布局属性

「动画为什么卡」——十次里有八次答案在这一页。两边做的是视觉上完全一样的移动， 左边用 x/y（transform），右边用 left/top（布局属性）。 把数量拉到 300 以上，差距就出来了。

✅ x / y / scale / opacity
走 合成层（compositor），由 GPU 直接搬运已经画好的图层。 不触发重排、不触发重绘，浏览器主线程几乎不用干活。
-- FPS
❌ left / top / width / height
每改一次都要重新计算布局（reflow），然后重绘。元素越多、层级越深，主线程负担越重， 一旦一帧算不完就掉帧。
-- FPS
元素数量 200 ×2
你想做的效果该用别用浏览器要干的活
左右上下移动x / yleft / top / margin合成 vs 重排+重绘
放大缩小scalewidth / height合成 vs 重排+重绘
淡入淡出autoAlphadisplay 切换合成 vs 重排
百分比位移xPercent / yPercentleft: "50%"合成 vs 重排
圆角 / 阴影变化—borderRadius / boxShadow重绘（可接受，但别用在几百个元素上）
颜色变化backgroundColor—重绘（不触发重排，代价中等）
 
// ❌ 触发重排：每帧都要重新计算整个文档的布局
gsap.to(box, { left: 400, top: 200, width: 300, duration: 1 });

// ✅ 只走合成层：GPU 搬运已有图层，主线程几乎不参与
gsap.to(box, { x: 400, y: 200, scaleX: 1.5, duration: 1 });

// ✅ 淡出用 autoAlpha 而不是手动切 display
//    autoAlpha = opacity + visibility，透明时自动 visibility: hidden
//    好处：元素彻底不再拦截鼠标点击，又不像 display:none 那样触发重排
gsap.to(box, { autoAlpha: 0, duration: 0.4 });

// 提前告诉浏览器「这个元素要动了，请单独提一个图层」
// 注意：只加在真正会动的元素上，滥用反而爆显存
.card { will-change: transform; }

为什么 GSAP 的 x/y 不是 left/top：这是 GSAP 的刻意设计。 它把 x 编译成 transform: translateX()，天然走合成层。 很多人从 jQuery 迁过来习惯性写 left，性能就白扔了。
will-change 不是越多越好。每个 will-change 元素都会被提升为独立图层，占显存。 在几百个元素上无脑加，反而比不加更卡。正确做法是只加在确实会动的少数元素上， 或者动画开始前用 JS 加、结束后移除。
实在必须动布局属性怎么办：用 Flip 插件——它的思路是「先让 DOM 变成最终布局，再用 transform 把视觉位置倒推回起点做动画」， 这样既改了真实布局，动画过程又全程走 transform。
